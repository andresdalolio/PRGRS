# Training integration implementation and verification

Date: 2026-11-07. Inputs: `PRGRS_DATA_MODEL.md`, `TRAINER_DATA_REQUIREMENTS.md`, `TRAINER_COMPATIBILITY_REPORT.md`, authoritative product/brand/reference documents, and the current source and migration chain. The discovery files are retained as historical inputs, not rewritten to imply these changes existed during discovery.

## Decisions and rationale

The requested deliverable is Trainer → PRGRS program import. It does not establish the closed-loop performance feedback system described in the discovery reports. The shared contract separates these explicitly. No training decisions, loads, exercise substitutions or progression are generated by PRGRS.

- Version 1 remains structurally compatible. Version 2 adds optional prescription targets for per-set work, effort, percentage denominator, side, pace/zone, progression, stopping and planned alternatives. Strict fields prevent unsupported structures from disappearing. V1 cannot accidentally accept V2 fields.
- Group rounds, recovery and conditioning timing remain authoritative block instructions. TR-015 explicitly permits human-readable protocols for display. V2 requires instructions for grouped/conditioning blocks. PRGRS neither runs timers nor claims machine-readable interval scoring. Nested groups are not required by current methodology.
- Per-set prescriptions stay inside the existing prescription JSONB. One occurrence remains one completion unit. Targets are separate from the existing actual load, notes and completion log. Zero observed effort, reps or load is never inferred from a target or checkbox.
- The existing transactional save/assign RPCs remain the persistence boundary with coach ownership and accepted-athlete checks. No browser write grants or RLS policies are broadened. New structural helper execution is revoked from public, anonymous and authenticated roles; it is called only through the already restricted validator/definer save path. The existing fixed search paths and explicit authorization remain in place. These choices follow the [Supabase database function guidance](https://supabase.com/docs/guides/database/functions).
- `20261107231502_training_contract.sql` adds `programs.contract_version`, `workout_sessions.position`, and `workout_sessions.provenance`. No training/result tables are added. Provenance captures source program UUID/name/description/revision/contract version at assignment. Old snapshots get null provenance and default position; no current mutable templates are used to reconstruct supposedly historical truth.
- The session reader and IndexedDB-backed app view both order by date, assignment, position, then UUID. Fixing only server order would fail because IndexedDB reads by primary key. Ordering between independent assignments is deterministic but carries no training priority. Position remains intact after program removal.
- Canonical library metadata is resolved visibly in preview. Its name, aliases and reference are the effective import values. The server locks canonical rows and rejects conflicting/stale metadata instead of silently assigning something different from preview. Save failure refreshes library metadata and requires another preview. Distinct variants require distinct stable keys.
- Existing owner/content uniqueness handles duplicate imports; explicitly selecting an existing program handles updates. There is no automatic name match. New assignments receive revised templates. All existing assigned sessions, including upcoming work, retain their original prescription. Durable source provenance survives program removal. Existing mutation, version, receipt and offline recovery behavior remains intact.

## Source and generated artifacts

Runtime definitions live in `src/lib/import.ts`. `npm run schema:generate` emits both `public/examples/program.schema.json` (v1 + v2) and `docs/integration/PRGRS_TRAINING_SCHEMA.json` (Trainer v2). Input-mode schema generation reflects optional defaulted fields correctly; Zod still supplies defaults when parsing. Generated database types were regenerated with `npm run db:types` using disposable PostgreSQL.

SQL embeds a frozen copy of each structural schema and validates the limited vocabulary used by those schemas, rejecting unknown validator keywords. This avoids adding a production extension/dependency and works in the existing disposable PostgreSQL test environment. Explicit SQL checks supplement structural validation for unique weeks, instruction eligibility, repeated exercise identity, group protocol and set-count ambiguity. Runtime validation performs the corresponding checks and reports field paths. Browser validation parses full URLs; SQL independently checks the http(s) scheme and URL shape. Neither validates external content or training prose.

Regression tests compare the published schemas with runtime generation and the migration's embedded structural schemas. A future contract change must use a new version/migration and deliberate test updates; do not rewrite an applied migration just to make a schema comparison pass. The checked-in migration is immutable after deployment. Changes to semantic rules also require both runtime and server coverage.

The legacy builder retains advanced fields on object edits, but dedicated controls for the additional v2 fields are not added; edit those targets in JSON and review the full preview. Prescriptions render through the shared formatter in preview, workout and exercise history. Targets retain their original text and units, except existing importer whitespace trimming and default normalization. `trainer-example.json` is a serialization fixture, not Trainer-authored programming advice.

## Requirement coverage and limits

| Requirement group  | Delivered / retained behavior                                                                                                                                                             |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TR-001–005         | Objectives in program description; priority, stimulus, time separation/reductions in workout description; relative numbered schedule, estimated duration and persistent same-day ordering |
| TR-010–015         | Ordered blocks/entries, empty instruction blocks, existing block kinds, mandatory v2 group protocol instructions; no executable timing                                                    |
| TR-020–024         | Stable coach-scoped variant keys, canonical conflict review, cues and external references; automatic movement classification deferred                                                     |
| TR-030–043         | Existing targets plus effort, percentage reference, sides and ordered warmup/work set details; stop criteria preserved                                                                    |
| TR-050, TR-060–062 | Alternatives, progression conditions and variable in prose; reduction intent in descriptions/instructions; no automatic decisions                                                         |
| TR-070–078         | Existing finish/skip/checklist/load/notes preserved; structured actual sets, effort, technique and substitutions are still absent                                                         |
| TR-080–094         | Cardio/stations/protocol prescriptions delivered; structured actual cardio, splits, scores and transitions absent                                                                         |
| TR-100–103         | Trainer may prescribe readiness/stop guidance; structured observed recovery/safety context absent                                                                                         |
| TR-110–113         | Assigned prescription snapshots, exact occurrence identity and durable source provenance retained; structured modification history absent                                                 |
| TR-120–122         | Eligible-entry completion and independent session finalization unchanged; per-set/round completion is not inferred                                                                        |
| TR-130–142         | No supported history feedback/export contract yet; explicit target units/reference prose retained, not treated as structured actual observations                                          |

The critical remaining dependency for autonomous Trainer progression is a separately designed actual-result and completed-history export contract, including actual variant identity, per-set metrics, cardio/splits, conditioning scores and recovery context. These unresolved feedback capabilities do not block faithful prescription delivery and must not be represented as implemented.

## Verification record

- `npm run lint`, `npm run typecheck`, and `npm test`: passed (67 unit tests).
- `npm run db:test`: passed: 60 existing PostgreSQL assertions plus the dedicated v2 delivery suite. Covers direct-RPC strict validation, full rich prescription round-trip, same-day assignment order, duplicate rejection, template update isolation, stable exercise IDs, incomplete finished history, canonical conflicts, provenance after removal and idempotent original mutation acknowledgement after detachment.
- `npm run schema:generate` and `npm run db:types`: completed.
- `npm run test:e2e`: passed, 14 tests across desktop Chromium and mobile WebKit, including the Trainer v2 invalid-file error, corrected preview, TikTok reference, assignment, IndexedDB reload, same-day priority, rich target display, three occurrence completion controls and empty actual-load input. The command also ran a successful production `npm run build`. An initial new test locator failed after refilling a controlled textarea; using its textbox role corrected the test, and the complete suite then passed.
- `npm run format:check`: the supplied `TRAINER_DATA_REQUIREMENTS.md` and `TRAINER_COMPATIBILITY_REPORT.md` have pre-existing formatting warnings. These methodology inputs were left unchanged. Generated integration documentation and modified code pass a separate targeted Prettier check.

Database tests use PGlite and an `auth.uid()` shim. Browser tests use the real migration/RLS/RPC implementation behind a local test HTTP adapter with simulated authentication. They do not verify hosted schema cache, email delivery or a real Supabase Auth/PostgREST deployment. No hosted migration, production reset, deployment or external account change is performed. The migration must be applied through the project's authorized deployment process before the new client can use it against a hosted database.
